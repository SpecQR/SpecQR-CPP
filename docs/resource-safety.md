# リソース上限と安全性の契約

SpecQR uses bounded inputs, strict UTF-8 and checked geometry. Allocation failures remain standard C++ exceptions; the library does not promise a fixed peak memory budget.

## 入力と容量は別の制約

| 対象 | 上限・動作 |
|---|---|
| 通常のテキスト入力 | UTF-8 で 1,000,000 バイト。上限超過は `INVALID_INPUT` |
| バイナリ入力 | 1,000,000 バイト。文字コード変換を行わない |
| 通常の手動セグメント | 制御セグメントを含めて 65,536 個。ペイロードの `byte_count()` 合計も 1,000,000 以下 |
| Model 2 | バージョン 1–40、最大 177 × 177 モジュール |
| Structured Append | 2–16 シンボル、入力合計 1,000,000 バイト。手動指定は 1–32,768 個の空でないデータセグメント |
| GS1 | 入力文字列 1,000,000 バイト、要素 16,384 個。対応する AI は限定カタログ内のもの |
| ラスター画像 | 一辺 2,048 ピクセルまで。RGBA 形式 |
| レンダリングの色・タイトル | 各 65,536 バイトまで。タイトルは XML 1.0 で利用できる正しい UTF-8 |

これらは処理資源の上限であり、そのデータ量が QR に格納できるという意味ではありません。`QRCode::estimate()` と `analyze_segments()` は容量不足を `Plan::ok == false` で返します。`generate()` と `generate_segments()` は同じ容量不足を `Error`、コード `DATA_TOO_LONG` で報告します。不正なモード・バージョン・入力は計画時点でも例外になります。

Kanji セグメントの `byte_count()` は Shift_JIS 相当の 1 文字 2 バイトです。テキスト API の入力上限は元の UTF-8 バイト数を使います。Structured Append のパリティ・結合検証ではテキストの元の UTF-8 バイト列を使用します。

## Unicode と数値

テキスト API は過長形式、不正な継続バイト、途中で切れた列、サロゲート、U+10FFFF を超える値を拒否します。Unicode 正規化は行いません。文字列長を明示した `std::string` / `std::string_view` の埋め込み NUL は保持します。生バイト API は任意のバイト列を保持します。

UTF-8 の復号、ビット操作、GF(256)、BCH、CRC は符号なし値を使用します。バージョン・マスク・列挙値・セグメント数を検証し、公開画像 API は寸法の乗算前に範囲を確認します。通常のシンボル生成で扱うビット数とコード語数は Model 2 の上限内です。

`Plan` と `Capacity` は利用者がコピー・編集できる値です。差分や積を返す算術ヘルパーは `std::int64_t` で計算するため、フィールドに `INT_MIN` / `INT_MAX` を設定しても符号付き整数オーバーフローを起こしません。計画を受け取る描画診断は評価バージョン 1–40 と非負のビット数を検証します。ただし、利用者が編集した計画が実際に生成された QR と一致することまでは証明しません。公開 API に任意の `Plan` からシンボルを構築する経路はありません。

## 最適化とメモリ

混在モードの最適化は Unicode スカラーごとに最大 7 状態の動的計画法を使います。Numeric の必要ビット数をすべてのテキストモードの下限として計算し、対象範囲の最大容量を超える入力には最適化状態を確保しません。内部にも 7,100 スカラーの最適化上限があります。この上限は単一 Model 2 シンボルの最大 Numeric 容量より大きい値です。

最適化は最大 3 種類の文字数フィールド幅（バージョン 1–9、10–26、27–40）について結果を再利用します。各幅に対する最適化時間・状態メモリは入力スカラー数に比例します。入力検証や UTF-8 索引のメモリは入力長に比例します。容量不足の大きな入力でも検証・セグメント保持のためのメモリは必要です。

PNG は組み込みの非圧縮 DEFLATE、Adler-32、CRC-32 で出力します。zlib / libpng は使用しません。生成中は RGBA や PNG の作業バッファが共存し、データ URL にはさらに Base64 文字列が必要です。一辺 2,048 ピクセルという制限はピークメモリ量の保証ではありません。SVG の座標は整数範囲を検証しますが、ラスター画像と同じピクセル上限はありません。

## 所有権・例外・並行利用

`Segment` と `QRCode` は入力を所有し、公開する内部データ参照は `const` です。共有可変キャッシュやプラットフォームの文字コード変換器はありません。同じ結果に対する `const` アクセスと、別々の結果の生成は並行利用できます。別スレッドでの代入・移動・破棄や、参照の寿命管理は利用者側で同期してください。

`Segment` の移動元は空の Byte セグメントにリセットされ、文字数と実データの一致を維持します。`QRCode` の移動元の内容は未規定です。再代入や破棄ができ、`QRCode::module()` は実際の格納行列を検査するため、移動後の空の格納領域を範囲外参照しません。移動元の計画情報と行列の一致には依存しないでください。

入力の検証エラーには `specqr::Error`（`std::invalid_argument` 派生）と安定した `code()` を使用します。通常のシンボル生成における `DATA_TOO_LONG` は必要ビット数・容量・評価バージョンも返します。高水準Structured Appendの分割失敗には単一シンボルの容量情報がない場合があります。メモリ確保失敗を別の意味の入力エラーへ置き換えず、`std::bad_alloc` などの標準例外は呼び出し元へ伝播します。出力ストリームへの書き込み失敗は `std::ios_base::failure` です。上限内の入力でも実行環境の空きメモリや出力先によって成功しない場合があります。

## Kanji 対応表の再生成

対応表はユーザー所有の [SpecQR-CSharp の固定コミット](https://github.com/SpecQR/SpecQR-CSharp/blob/057c4b3f25e52c4786a8f94c744ff884eedcecfa/src/SpecQR/KanjiMap.cs)にある Unicode / Shift_JIS の文字対応データを変換したものです。元データは SpecQR-Swift の WHATWG Shift_JIS 復号対応表に由来します。第三者 QR エンコーダのコードは含みません。

Python はこの開発用の検証にだけ必要です。ライブラリのビルド・実行には不要です。固定コミットから取得した `KanjiMap.cs` に対して実行します。

```sh
python3 tools/generate-kanji-map.py --source path/to/KanjiMap.cs --check
# 更新したい場合は --check を外す
```

スクリプトは元の圧縮文字データの SHA-256、重複、QR の Shift_JIS 範囲、13 ビット値、6,953 エントリを検査します。対応表はコンパイル時の読み取り専用配列になり、実行時にダウンロードや初期化用のメモリ確保を行いません。
